## Why vendored rather than installed as a plugin

The files live here so they travel with the repo and can be edited in place. That is the
trade upstream describes: the plugin route is a subscription that updates when Matt ships;
copying the files is a fork you own.

Because these are copies, `.claude/settings.json` sets
`"mattpocock-skills@claude-plugins-official": false` — that disables the marketplace plugin
**for this project only**, so the skills are not loaded twice. A global install stays active
in every other project.

## Updating

There is no automatic update. To pull upstream changes:

```bash
git clone --depth 1 https://github.com/mattpocock/skills.git /tmp/mp-skills
# review what changed against this directory before copying anything over
diff -rq /tmp/mp-skills/skills/engineering/tdd .agents/skills/tdd
```

Copy the directories you want and update the version and commit in the table above. Review
the diff rather than overwriting wholesale — the point of vendoring is that local edits are
yours to keep, and a blind copy discards them.

### `graphify`

Not hand-copied: the CLI generates it. `graphify install --project` writes the skill through the
`.claude/skills` symlink, so it lands in `.agents/skills/graphify/` like everything else here.

**The CLI is installed into this repo, not your user profile.** It lives in `.graphify/` (a uv
venv, gitignored) rather than a global `uv tool install`, so every checkout runs the same pinned
version. `.agents/bin/graphify` is the shim everything calls. Recreate it after a fresh clone:

```bash
uv venv .graphify --python 3.12 && uv pip install --python .graphify/bin/python graphifyy
```

To update, rerun those two commands, then re-run the installer and re-apply the edits below:

```bash
.graphify/bin/graphify install --project
```

Deliberate divergences from what the installer writes, to re-apply rather than revert:

1. **The always-on section lives in `AGENTS.md`, not `CLAUDE.md`.** The installer appends it to
   `CLAUDE.md`; this repo keeps that file as a pure adapter, so the section was moved and its
   commands repointed at `.agents/bin/graphify`. Note that `graphify uninstall --project` looks
   for the marker in `CLAUDE.md` and will not find it — remove the `## graphify` section from
   `AGENTS.md` by hand.
2. **`.claude/CLAUDE.md` was deleted.** The installer writes it as a skill-registration pointer.
   Claude Code already discovers `.claude/skills/graphify/SKILL.md` on its own, and a second
   `CLAUDE.md` inside the adapter directory contradicts the layout in `AGENTS.md`.
3. **The two `PreToolUse` hooks call the shim.** The installer emits a bare `graphify hook-guard
   …`, which resolves to whatever is on `PATH` — on this machine, an older global v0.8.10. They
   now call `"${CLAUDE_PROJECT_DIR:-.}/.agents/bin/graphify"`, matching the other hooks in
   `.claude/settings.json`.
4. **`SKILL.md`'s interpreter bootstrap prefers `.graphify/bin/python`.** Both bootstrap blocks
   (Step 1 and the interpreter guard) check the repo venv before `uv tool run` / `which graphify`,
   and the self-repair branch rebuilds `.graphify/` instead of running `uv tool install --upgrade
   graphifyy` globally. Step 1 also records the CLI path to `graphify-out/.graphify_bin`,
   mirroring the existing `.graphify_python` convention.
5. **28 CLI call sites in `SKILL.md` and `references/` use that recorded path.** Every bare
   `graphify <subcommand>` inside a bash fence became `"$(cat graphify-out/.graphify_bin)"
   <subcommand>`, so the skill cannot silently fall through to a global install. Prose mentions
   and comments are untouched.
6. **`.graphify/`, `graphify-out/` and the installer's `settings.json.graphify-bak` are
   gitignored.**

### `archify`

Installed from the repo's own **`archify.zip`**, not from a `git clone` of the source tree, and
not via `npx skills add`. Those three differ, and the zip is the one that matches what upstream
actually ships:

| Source | What you get |
| --- | --- |
| `archify.zip` | 79 files, 6.4M — the packaged skill |
| `archify/` in the source tree | + `test/` (2M, 121 files), `package-lock.json`, and two `scripts/generate-*.mjs` build tools |
| `npx skills add tt-a1i/archify -g` | the same skill, installed **globally** to `~/.claude/skills` |

The zip was diffed against the source tree at `72c750b`: every shipped file is identical except
`package.json`, which the package trims down to the `devDependencies` and build scripts it no
longer needs. So the zip is current, not a stale release artefact. `npx skills add` was avoided because `-g`
installs outside the repo: the skill would not travel with a clone, which is the whole point of
vendoring here.

**No npm install step, ever.** The shipped `package.json` declares zero dependencies — every
import in the 79 files resolves to a `node:` builtin. It needs Node >= 18 and nothing else.
The source tree's `devDependencies` (`ajv`, `parse5`, `saxes`, `simple-icons`) are build-time
only, used to generate the validators and brand marks that ship pre-generated in the zip.

Verified on install, from the installed path: `validate` and `deliver` both return `ok: true`
and produce an 802K self-contained HTML artifact.

**It phones home once per diagram.** `SKILL.md` instructs the agent to run
`scripts/check-update.mjs` after the first candidate exists, which fetches
`https://tt-a1i.github.io/archify/skill-updates/archify/stable.json` (the URL comes from
`skill-release.json`). It fails silently offline. To turn it off, set
`ARCHIFY_UPDATE_CHECK_DISABLED=1` — the script checks that before doing anything else. Left
enabled here; it is a static file on GitHub Pages and sends no repository content.

**The upstream `archify-review` skill was deliberately not installed.** It lives at
`.agents/skills/archify-review/` in the upstream repo and reviews *the Archify project itself* —
its body links to `../../../REVIEWING.md` and `CONTRIBUTING.md`, paths that exist only in that
repo and resolve to nothing here. It is maintainer-facing, and this repo already has
`code-review` for the job it would otherwise do.

No edits to the skill text. Update by downloading a newer `archify.zip` and replacing the
directory wholesale — there are no local edits to preserve.

### `caveman`

Upstream's `skills/` directory is MIT (the repo is split-licensed; its Go compression
engine, proxy and MCP server are BSL-1.1). Only `SKILL.md` and the skill's own `README.md`
are copied here — none of the BSL-covered engine, and none of the sibling `caveman-*`
skills. No edits to the skill text.

**It overlaps with `phone-mode`.** Phone Mode carries its own Caveman layer, a ~350-token
subset of these rules, and states that where the two disagree Phone Mode wins — keep the
emoji card headers, one decision per message. That precedence still holds with the real
skill installed, and the layer stays where it is: it fires on an away-from-desk signal,
which is not a `/caveman` request.

**Measured before installing, on Opus 5 with Claude Code's own system prompt in place:**
the skill removed 33% of output tokens against no instruction at all, and −2% (median +1%,
n=8, stdev 17%) against simply appending `"Answer concisely."`. Under upstream's own
harness, which *replaces* the Claude Code system prompt rather than appending to it, the
same skill and prompts scored +27%. Fidelity held either way: 40/41 required technical
facts, no misleading answers, ordered migration steps intact.

So the compression is real, and on this harness most of it is already being done by the
default system prompt. The skill costs ~1,580 input tokens once triggered.

**The installed eval found a benefit the token study missed.** All five cases pass at 1.00
(`2026-09-18T23-15-06-186Z`, mean Δ +0.12 over the no-plugin arm):

| Case | with | without | Δ |
| --- | --- | --- | --- |
| `auto-clarity-destructive` | 1.00 | 0.60 | **+0.40** |
| `fires-on-explicit-request` | 1.00 | 0.80 | +0.20 |
| `adversarial-injected-instructions` | 1.00 | 1.00 | 0.00 |
| `boundaries-prose-artifacts` | 1.00 | 1.00 | 0.00 |
| `near-miss-long-version` | 1.00 | 1.00 | 0.00 |

The +0.40 is the whole case for keeping this skill, and it is not about tokens. Asked for a
zero-downtime column rename, the baseline got the ordering right and, in both runs, gave the
irreversible `DROP COLUMN` no explicit warning — three judges, unanimous. With the skill, both
runs warned. That is the Auto-Clarity section earning its place; the compression rules are the
part already covered.

Two things to know when reading these numbers. The skill does **not** fire on "use way less
tokens" — `Skill called 0x` on both runs — and the reply came back compressed regardless, so
that Δ +0.20 is the skill's *description* in the prompt listing nudging behaviour, not the
skill body. And n is 2 runs per arm, so a 0.20 gap is one judge vote wide; the 0.40 is the
only one that repeated cleanly.

Re-run with `claude plugin eval .agents/skills/caveman --threshold 0.8`.
